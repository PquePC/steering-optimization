# 04 — Gate 1 anchors from this run, and make it an instrument gate

**Status:** DECIDED. Implement as written. Needs ~24 hand labels from the operator, once.
**Blocking:** yes.

## Goal

Gate 1 selects its two anchor cells from **this run's own scan surface** by objective criteria, and
is keyed on the **judge configuration** rather than the concept — so the operator labels once, not
once per concept.

## Why

Gate 1 asks: **is `e5` reading influence, or is it counting how often the concept word appears?**

`e5` is the primary effectiveness metric and `E5_FLOOR` sits in the selection rule, so an `e5` that
counts words makes "qualifies" meaningless and the entire result unpublishable. This is worth the
operator's time.

Its criterion is **not** the correlation with the labels. It is a **≥ 3.0 separation on the 0–10
scale between two anchor cells**, picked so that a word-counting judge gets both backwards:

- **anchor HIGH** — real output drift, but the concept's own token is unreachable. A judge reading
  influence scores this high; a judge counting words scores it near zero.
- **anchor LOW** — no drift, but the concept word happens to be present and high-ranked. A word
  counter scores this high; a judge reading influence scores it near zero.

If `e5(HIGH) − e5(LOW) ≥ 3.0`, the judge is reading influence. The rank correlation against the
full label set is reported alongside as a **diagnostic only** — the source says so outright, "50
labels do not make a correlation a criterion" — so do not inflate the labelling burden chasing it.

v1 used Pillows L46 α=4 and Silk L46 α=2. Those cells came from a run whose data is gone, and they
are *other concepts* — the portability problem in [`BRIEF.md`](BRIEF.md) §5. But **both properties
are objective and this pipeline already measures them**: concept-token probability and rank are
exactly what `d3` and `e6` compute. The anchors can be found in any run, on any model, for any
concept.

## What to change

1. **Select both anchors from this run's scan surface** by the objective criteria above. Record the
   measured probability and rank that justified each pick — not just which cell was chosen. A gate
   that does not say why it chose its anchors is not auditable.
2. **Generate the steered/unsteered response pairs** at both cells.
3. **Produce a labelling file for the operator**: prompt, unsteered response, steered response,
   blank score, ~12 per anchor. **Do not tell the operator which anchor a transcript came from, and
   do not order them by anchor** — shuffle. Otherwise the labels inherit the hypothesis and the
   gate grades its own expectation.
4. **Write `gate1_hand_labels.jsonl`** in the schema `gates.py` already documents (`concept`,
   `layer`, `alpha`, `prompt`, `response_unsteered`, `response_steered`, `hand_label`) and resolve
   it through `$M2_M15_DIR` as now.
5. **Key the stored label set on the judge configuration** — judge model plus judge prompt version —
   and reuse it across concepts until that configuration changes. Record which configuration a
   given label set certifies, and make the gate **refuse to reuse labels from a different judge
   configuration** rather than silently accepting them.

## Why the labels must come from the operator

A label file generated by any part of this pipeline is the pipeline grading its own work. This step
is irreducible and the code must not offer a way around it — no "auto-label with a second model"
fallback, no default that fills them in.

## Acceptance

- A test that trips it: synthesise judge scores that rank LOW above HIGH and confirm the gate
  **fails**.
- The gate output names both anchor cells, the measured probability and rank behind each, the
  separation, and the judge configuration the labels are keyed to.
- Reusing a label set against a changed judge configuration is refused with a clear message.
- The labelling file is presented to the operator shuffled and unlabelled as to anchor.
